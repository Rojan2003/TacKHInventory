# Security design and review

## Authentication and authorization

| Layer | Mechanism |
|-------|-----------|
| Identity | Google Identity Services "Sign in with Google" button (popup). The browser receives a signed ID token. Only the public OAuth client ID is used; no client secret exists in the project. |
| Verification | `auth.login` sends the ID token to the Apps Script. The backend calls Google's `tokeninfo` endpoint over HTTPS and re-checks `aud` (must equal `GOOGLE_CLIENT_ID`), `iss`, `exp` and `email_verified`. Apps Script has no RSA primitives, so Google performs the signature check; this is a supported, documented flow. |
| Allowlist | The verified email must exist and be active in the `AuthorizedUsers` worksheet. The initial administrator is seeded server-side by `setup()` (and, as a fallback, on the first login of that exact address when the sheet is empty). |
| Session | The backend issues `base64url(payload).base64url(HMAC-SHA256(payload, SESSION_SECRET))` with an 8-hour expiry. `SESSION_SECRET` lives only in Script Properties. Signature comparison is constant-time. The token is stored in `localStorage` on the client; `rotateSessionSecret()` invalidates every session. |
| Per-request | Every protected action re-verifies the token and reloads the user, so deactivation or role changes are effective immediately (60 s cache). The browser never supplies its email or role. |
| Roles | `admin`, `literature_servant`, `congregation_user`, `read_only`. The permission matrix is in `apps-script/src/00_Config.js` and is enforced in every handler. Congregation users are additionally scoped to their own congregation for requests, distributions, stock views and reports. Frontend route guards and hidden buttons are UX only. |
| Admin safety | A user cannot deactivate themself or drop their own admin role; the last active administrator cannot be removed. |

## Transport

Apps Script cannot answer CORS preflight requests, so the client sends `POST` with `Content-Type: text/plain`
and the token inside the JSON body, over HTTPS. `GET` serves only a health payload. Responses never include
stack traces; unexpected errors are logged server-side with the request ID and reported to the client as a
generic message.

## Data integrity

- Every mutation runs inside `LockService.getScriptLock()` and requires a client `requestId`; a repeat of the same
  `(actor, requestId)` returns the stored response without re-executing (IdempotencyKeys sheet + cache).
- Ledger rows are append-only; balances are derived and can be rebuilt (`admin.reconcile`).
- Negative stock is rejected before any write. Approvals cannot exceed available stock when reservation is on.
- Multi-sheet writes are ordered so interruptions are detectable (distribution `Processing` status) and repaired by
  reconcile. Google Sheets provides **no** transactional guarantees; this is a mitigation, not a transaction.
- CSV exports neutralise cells starting with `= + - @` to prevent formula injection when opened in a spreadsheet.
- Input is validated server-side (types, ranges, lengths, enumerations, duplicate lines).

## Caching

- **Backend**: raw worksheet rows are cached in CacheService for 120 s under a key that embeds a global data
  version. Any write bumps the version (in a `finally` block, so a failed mutation still invalidates); a missing or
  evicted version key yields a brand-new version, never an old one. Reads inside the script lock bypass the cache
  and never populate it, so stock checks, approvals, releases and reconcile always see the sheet. `AuthorizedUsers`,
  `AuditLogs` and `IdempotencyKeys` are never cached; only raw rows are cached, never per-user responses. Values
  over 90 KB are not cached. `CACHE_ENABLED=false` disables it; `admin.clearCache` (administrators) bumps the version.
- **Browser**: TanStack Query keeps fetched pages in memory with stale-while-revalidate (30 s) and invalidates
  related families after every successful mutation. Only items, stock, dashboard, congregations, deliveries,
  requests and distributions are persisted to `sessionStorage`, keyed by user id; users, audit and settings never
  are. Logout, a 401 and session expiry wipe memory and storage.

## What is public by design

- The OAuth client ID and the Apps Script `/exec` URL (compiled into the GitHub Pages bundle).
- The spreadsheet ID (inside the backend code only; it is not a credential).
- The GitHub repository and the built frontend.

## Outstanding risks and limitations

1. **Spreadsheet sharing** and the **legacy endpoint** are live exposures until the manual steps are done.
2. The web app must be deployed with access "Anyone" to be callable from GitHub Pages. Unauthenticated callers can
   reach `health` and `auth.login` only; there is no rate limiting beyond Apps Script quotas. If abuse becomes a
   concern, the fallback is hosting the UI inside Apps Script `HtmlService` with "Anyone with Google account".
3. `tokeninfo` is an external dependency at login time; an outage blocks new sign-ins (existing sessions keep working).
4. Session tokens in `localStorage` are exposed to any XSS. The app loads only first-party code and Google's GIS
   script; keep it that way and keep dependencies updated.
5. The fake runtime used for tests models Apps Script behaviour (locks, sheets, properties) but is not Google.
   Production verification of concurrency and quotas still requires the manual test plan in `TESTING.md`.
6. The first-login fallback that seeds the initial administrator only applies while `AuthorizedUsers` is empty and
   only for the exact configured address; `setup()` normally seeds it first.
7. GitHub Actions uses repository *variables* (public) only; no deployment secret exists to leak. Do not add any.
